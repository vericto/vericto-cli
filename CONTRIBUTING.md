# Contributing to vericto-cli

Thanks for your interest in improving the Vericto CLI. This guide covers the
`vericto` command in this repository, which is open source under the
[GNU Affero General Public License, version 3 only](LICENSE)
(AGPL-3.0-only) and also available under a commercial license (see
[LICENSING.md](LICENSING.md)). Contributions are accepted under the Vericto
[Contributor License Agreement](#license-and-contributor-license-agreement).

## Code of Conduct

This project follows the [Contributor Covenant](CODE_OF_CONDUCT.md). Be
respectful, constructive, and technically precise.

## What belongs here

The CLI is a thin client: it sends SQL to the Vericto API and mirrors the
verdict as an exit code (see [DESIGN.md](DESIGN.md)). Contributions that fit
here:

- **Commands and flags** — `check`, `login`, `doctor`, `init`, `verify-receipt`
  and the rest of `src/`.
- **Reports** — the `text`, `json`, `sarif`, `gitlab-codequality` and
  `gitlab-sast` formats, and CI annotations.
- **Authentication** — API keys, the config file, OIDC workload identity.
- **File selection and sanitized mode** — `--changed`, `--since`, baselines,
  `.vericto.toml`, the SQL sanitizer.
- **Distribution** — the cargo-dist configuration (`dist-workspace.toml`), the
  npm installer (`npm-installer/`), the `Dockerfile`, and the publish workflows
  for npm and Homebrew.
- **Documentation** — `README.md` and `DESIGN.md`.

Contributions that belong elsewhere:

- A statement that got the wrong verdict, a new rule, SQL parsing →
  [vericto-engine](https://github.com/vericto/vericto-engine).
- The GitHub Action (`uses: vericto/check-sql@v1`) →
  [check-sql](https://github.com/vericto/check-sql).
- The Homebrew formula is generated and published from this repository; do not
  edit it in [homebrew-tap](https://github.com/vericto/homebrew-tap).

## Getting started

```bash
git clone https://github.com/<you>/vericto-cli.git
cd vericto-cli
cargo build
cargo test
```

Requires Rust 1.88+ (`rust-version` in `Cargo.toml`), a C compiler, libclang
and clang's own headers: the default `offline` feature embeds `vericto-engine`,
whose `pg_query` compiles PostgreSQL's parser and runs bindgen.

- macOS: the Xcode Command Line Tools (`xcode-select --install`).
- Debian/Ubuntu: `sudo apt-get install clang libclang-dev` (`libclang-dev`
  alone lacks `stdbool.h`); add `musl-tools` to build for
  `*-unknown-linux-musl`, as the release does.
- Alpine: build in a Debian container instead (see `Dockerfile`); the
  `rust:*-alpine` images cannot load libclang from a build script.
- Windows: the Visual Studio Build Tools (MSVC, "Desktop development with
  C++") and LLVM for libclang (`winget install LLVM.LLVM`; set `LIBCLANG_PATH`
  to its `bin` folder if bindgen does not find it). Windows on ARM64 builds
  natively with the same tools. CI runs the whole suite on `windows-2022` and
  `windows-11-arm`.

`cargo build --no-default-features` builds the thin client alone, without the
engine and without these prerequisites. The npm installer and Windows
packaging tests need Node 18+ and no dependencies. Tests never reach the real Vericto API: the
API client is tested against an in-process `wiremock` server, and
`tests/cli.rs` runs the built binary, each run with its own empty home.

## Development workflow

1. Fork the repo and create a branch: `feat/my-flag` or `fix/sarif-paths`.
2. Make your change with tests.
3. Run the checks CI runs before opening a PR (CI also sets
   `RUSTFLAGS="-D warnings"`, so a warning fails the build):
   ```bash
   cargo fmt --all --check
   cargo clippy --all-targets --all-features -- -D warnings
   cargo clippy --all-targets --no-default-features -- -D warnings
   cargo build --locked --all-targets
   cargo test --locked
   cargo test --locked --no-default-features
   (cd npm-installer && npm test)
   (cd windows && npm test)
   ```
   The `--no-default-features` runs are the thin client, where the engine is
   absent and `--offline` exits 2. The tests that run the PowerShell installer
   (`windows/`) and install a .zip through the npm package run on Windows
   only; elsewhere they are skipped.
   If you change dependencies, also run the supply-chain job
   (`cargo-deny` 0.20.2 and `cargo-audit` 0.22.2):
   ```bash
   cargo deny --locked check
   cargo audit --deny warnings
   ```
4. Open a PR using the template. Keep PRs focused and under ~500 lines.

### Coverage

CI does not gate on coverage. Line coverage of the unit and integration tests
is 92.3% (1.9.0, default features), measured with
[cargo-llvm-cov](https://github.com/taiki-e/cargo-llvm-cov); keep it there:

```bash
cargo llvm-cov --summary-only
```

New code comes with tests for its main and its failure paths (exit codes 2, 3
and 4 included).

### Generated files

`.github/workflows/release.yml` is generated by cargo-dist 0.32.0. Do not edit
it by hand: change `dist-workspace.toml` and run `dist generate`. The release
workflow's `plan` job runs on every pull request and fails if the two drift
apart.

## Commit convention

We use [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(dialects): Snowflake and SQLite; sanitized mode keeps bind parameters
fix(deps): rustls 0.23.46 and quinn-proto 0.11.18
test(cli): give every spawned vericto its own empty home
ci(docker): one `latest` tag, and a manual run on a branch only builds
```

Scopes used in this repo: `cli`, `dialects`, `dist`, `docker`, `deps`,
`security`, `license`, `readme`, `design`, `changelog`.

**Write in English** — commit subjects and bodies, code comments, test names,
identifiers, `CHANGELOG.md` entries and pull request descriptions.

## Changelog

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Add an entry under `## [Unreleased]` for any change a user can see (a flag, an
output format, an exit code, an installer, a dependency with a security fix),
in the section that fits: `Added`, `Changed`, `Fixed`, `Security`, `Tests`.
Changes to repository files that do not ship (CI, templates, this guide) need
no entry. Maintainers move the entries into a version section when they cut a
release.

## Pull request acceptance criteria

- ✅ Required checks pass: `Format (rustfmt)`, `Lint (clippy)`,
  `Build & test` and `CLA`. The other jobs (`npm installer tests`,
  `cargo-deny + cargo-audit`, the `gitleaks` secret scan and the release
  `plan`) run too and should be green.
- ✅ The Contributor License Agreement is signed.
- ✅ New behavior has tests; `CHANGELOG.md` updated under `[Unreleased]` when
  a user can see the change.
- ✅ At least one maintainer review (CODEOWNERS requests it).
- ✅ No new `unwrap()`/`expect()` on runtime paths — handle errors explicitly.

Pull requests are merged with a merge commit; squash and rebase merges are
disabled.

## Releases

Releases are cut by the maintainers:

1. Bump `version` in `Cargo.toml` (and `Cargo.lock`), the
   `@vericto/vericto-cli@X.Y.Z` pins in `.pre-commit-hooks.yaml` and the
   `rev: vX.Y.Z` of the README's pre-commit example (the installer tests fail
   until all three match), and turn `## [Unreleased]` into
   `## [X.Y.Z] - YYYY-MM-DD` in `CHANGELOG.md`, in a pull request.
2. After it is merged, tag the merge commit `vX.Y.Z` and push the tag.
3. The tag starts `release.yml` (cargo-dist): it builds the archives for every
   target, their SHA-256 checksums and build attestations, and creates the
   GitHub release. From there, `npm-publish.yml` publishes
   `@vericto/vericto-cli` and `homebrew-publish.yml` pushes the formula to
   [vericto/homebrew-tap](https://github.com/vericto/homebrew-tap); both wait
   for approval of the `prod` environment. `docker.yml` publishes
   `ghcr.io/vericto/vericto-cli` from the same tag.

Release tags (`v*.*.*`) are protected: once pushed, they cannot be moved or
deleted.

Do **not** open a public issue for vulnerabilities. See [SECURITY.md](SECURITY.md)
or email [security@vericto.com](mailto:security@vericto.com).

## Third-party and AI-assisted material

Do not copy code or documentation from an issue, comment, website or other
source unless the pull request identifies the source and Vericto has rights to
include it. Ideas and facts are different from copyrightable text or code.

Read [AI_POLICY.md](AI_POLICY.md). If an AI or code-generation tool assisted
the pull request, disclose it in the description using:

```text

```

You remain responsible for understanding, testing and licensing the submitted
material. Do not name an AI system in a `Co-authored-by` trailer.
